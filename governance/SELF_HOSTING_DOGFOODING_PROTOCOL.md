# Self-Hosting and Dogfooding Protocol

## Purpose

Use the real construction of Project Foundry as the first reference project and extract reusable, validated pipeline knowledge from actual challenges.

## Observation flow

```text
Observed event
→ fact record
→ challenge or opportunity
→ candidate lesson
→ generalization assessment
→ solution-method Decision Intelligence
→ bounded validation
→ explicit promotion
→ protocol / schema / validator / fixture / UX rule
```

## What must be observed

- loss or distortion of the North Star;
- scope drift;
- status overstatement;
- repeated owner confusion;
- repeated model ambiguity;
- missing evidence;
- ineffective decision methods;
- difficult handoffs or session recovery;
- repeated repository conflicts;
- successful patterns worth standardizing.

## Promotion rule

An observation does not become a permanent system rule automatically.

Promotion requires:

1. a source-bound observation;
2. a candidate lesson;
3. a generalization assessment;
4. a selected carrier;
5. evidence from real use or a fixture;
6. explicit authority;
7. a recorded promotion entry.

## MVP monitoring model

The initial implementation uses manual structured checkpoints plus repository and PR evidence. Automatic background monitoring is deferred. LLM analysis assists classification but cannot silently promote a rule.

## Output carriers

A validated lesson may be promoted to:

- protocol rule;
- schema field;
- validator rule;
- adversarial fixture;
- owner UX requirement;
- agent prompt contract;
- execution control;
- new pipeline stage.
